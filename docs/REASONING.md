# Health anomaly detection — reasoning, method and limits

How the machine-learning layer over dog health observations works, why it is
built this way, and — most importantly — what it does not claim.

> **It does not diagnose.** It scores how unusual a recorded observation is
> against the same dog's recent history, so a person can decide whether to look
> closer. It identifies no condition, rules nothing out, and is not veterinary
> advice.

---

## 1. The problem

**Task.** Unsupervised anomaly detection over longitudinal health observations.

**Question asked:** *does this observation look unlike the ones before it, for
this dog?*

**Question deliberately not asked:** *what is wrong with this dog?* Nobody has
labelled any observation as clinically concerning, and inventing such labels
would be inventing medicine.

### Why this is not the same as the Phase 4 rules

The deterministic engine in `health_intelligence.py` already answers fixed
questions: is a follow-up overdue, has weight fallen by 10% or more, is the
latest temperature past a monitoring threshold. Those are transparent,
auditable, and they will always be the first thing an admin reads.

What they cannot do is notice a *combination*. A 4% weight drop, a 0.9 °C rise
and a gap twice the usual length each sit under their own threshold, and each
is individually unremarkable — together they are the sort of thing worth a
second look. The model is there for that, and for scaling to a dog's own
normal: 0.5 kg means nothing for a 40 kg dog and a great deal for a 5 kg one.

The two layers stay separate everywhere — in the analysis response, in the
database, in the alert queue and on screen — because they answer different
questions with different reliability.

## 2. Data

### What is actually in the application

Almost nothing: the local demo fixture holds 2–4 observations per dog for five
dogs. That is not a training set, and pretending otherwise would be the
dishonest move here.

### What the model was trained on

**Synthetic development data**, generated by `ml/health_anomaly_data.py`:
420 simulated dogs, 12 observations each, about 5,000 observations. Each dog
follows one labelled scenario:

| Scenario | Planted as unusual? |
|---|---|
| `stable` | no |
| `gradual_weight_gain` | no — slow steady gain is ordinary |
| `gradual_weight_decline` | yes |
| `sudden_weight_drop` | yes |
| `isolated_temperature_spike` | yes |
| `repeated_abnormal_temperature` | yes |
| `irregular_observation_spacing` | yes |

Roughly 70% of dogs are normal, because a detector trained on a mostly-odd
population learns that odd is normal.

**What that means for the result:** the model has learned this generator's idea
of an unusual reading, not a vet's. It is a reasonable prior for "this does not
match the recent pattern" and nothing more. Replacing this with real
observations, once the rescue has accumulated them, is the single biggest
improvement available.

The synthetic data is never written to any database. `medical_demo_data.py` is
a separate, local-only fixture for the app itself.

## 3. Features

`ml/health_features.py` produces one row per observation, describing it
*relative to the history before it*. Raw values are useless across dogs of
different sizes; deviations are not.

| Feature | Meaning |
|---|---|
| `weight_pct_change` | % change from the previous weight |
| `weight_dev_from_baseline` | % away from the rolling mean (last 5 weigh-ins) |
| `weight_z` | deviation in rolling standard deviations |
| `weight_slope_pct` | % change per day since the previous weight |
| `temp_change` | °C change from the previous reading |
| `temp_dev_from_baseline` | °C away from the rolling mean |
| `temp_z` | deviation in rolling standard deviations |
| `days_since_previous` | gap to the previous observation |
| `interval_ratio` | that gap against this dog's usual gap |

**Only fields that exist** are used: `observation_date`, `weight_kg`,
`temperature_c`. Symptoms are stored as free-text strings and are not modelled.

**No future leakage.** A row for observation *i* is built from observations
*0…i−1* plus *i*. A row never changes when later observations arrive — a test
recomputes prefixes and asserts the earlier rows are byte-identical.

**Missing data is not faked.** A dog with fewer than 4 observations produces no
rows at all. A dog with no weights is still scored on temperature, and the
response records which measurements were considered. A fabricated zero would
read as "no change", which is a different claim from "unknown".

**Guards.** Rolling standard deviations have a floor (0.15 kg, 0.10 °C) so a
dog whose readings have been identical does not produce an infinite deviation.

## 4. Model choice

**IsolationForest**, inside a `StandardScaler` pipeline.

Chosen because:

* **No distributional assumption.** Percentage changes and z-scores are skewed
  and heavy-tailed; a Gaussian method would flag ordinary readings in the tails.
* **Multivariate by construction.** It isolates points by random splits, so a
  row unusual in a *combination* of features is caught even when no single
  feature crosses a threshold — precisely what the rules cannot do.
* **Cheap.** Under a second to train, microseconds to score, no GPU, no tuning
  theatre.
* **Honest output.** A continuous score, not a fake probability.

Rejected: a one-class SVM (slower, kernel-sensitive, no gain here); LOF (no
clean way to score a new point against a stored model); anything supervised
(there are no real labels).

### Parameters, and why they are what they are

| Parameter | Value | Why |
|---|---|---|
| `n_estimators` | 300 | More than the default 100; scores stop moving beyond this and training is still sub-second |
| `max_samples` | 256 | The library default heuristic; small subsamples are what makes isolation work |
| `contamination` | fitted from the data (≈0.06) | Set from the generator's planted rate rather than guessed. It sets the flag threshold, not the ranking |
| `random_state` | 20260923 | Fixed, so the artifact is reproducible |

## 5. Training and evaluation

```bash
cd app/backend
python -m ml.train_health_anomaly_model            # train, evaluate, save
python -m ml.train_health_anomaly_model --report   # print the saved metadata
```

Training is **unsupervised** — only the feature matrix is passed. The scenario
labels exist solely to measure afterwards.

**Split by dog, never by observation.** Rows from one dog share a baseline, so
splitting rows would put a dog's history on both sides and flatter the result.
294 dogs train, 126 are held out.

### Results on held-out dogs

| Metric | Value |
|---|---|
| Recall on planted anomalies | **0.70** |
| Precision | **0.66** |
| Share of observations flagged | 0.07 |

Per scenario:

| Scenario | Result |
|---|---|
| `sudden_weight_drop` | 1.00 detected |
| `isolated_temperature_spike` | 1.00 detected |
| `irregular_observation_spacing` | 1.00 detected |
| `gradual_weight_decline` | 0.91 detected |
| `repeated_abnormal_temperature` | **0.30 detected** |
| `stable` | 0.011 false positives |
| `gradual_weight_gain` | 0.017 false positives |

**These are not clinical accuracy figures.** They say how reliably the model
reproduces patterns a generator planted.

### The one weak result, explained

`repeated_abnormal_temperature` scores 0.30, and that is a consequence of the
design rather than a bug. The baseline is *this dog's recent readings*, so the
first raised temperature stands out strongly — and by the third, the raised
value has become the dog's normal, and it no longer looks unusual. A sustained
shift is exactly what a rolling baseline stops seeing.

This is the clearest illustration of why both layers exist: the deterministic
rule `temperature.repeated_abnormal` catches sustained abnormality against a
fixed monitoring threshold, which is a question no adaptive baseline can
answer. The rules cover the level; the model covers the change.

was fitted on synthetic rows only.

## 7. Inference

`ml/health_anomaly_service.py` loads the artifact once into a module-level
cache, the same pattern as the other models. **Nothing trains on a request.**

Severity comes from where a flagged score sits against the *training*
distribution recorded in the artifact: at or above the 99th percentile is
`high`, at or above the 90th is `moderate`, otherwise `low`. Those percentiles
are measured, not invented.

The score is reported as `anomaly_score` — higher means further from the dog's
usual pattern. It is **not** a probability, and the response says so in the
payload itself.

### Fallbacks

Nothing here can break the health analysis around it. Every failure returns a
reason:

| Reason | When |
|---|---|
| `insufficient_history` | fewer than 4 observations, or none comparable |
| `model_unavailable` | artifact missing or corrupt |
| `feature_schema_mismatch` | the artifact's feature list differs from `health_features.py` |
| `scoring_failed` | malformed rows, or feature computation failed |

`feature_schema_mismatch` has its own reason because the fix differs. Features
are positional: the model reads column 3 as `weight_slope_pct` because that is
where it sat during training. If a feature is later added, removed or
reordered, an older artifact would still accept the matrix and score it against
the wrong columns, producing numbers that look plausible and mean nothing. The
service compares the artifact's stored feature list against the current one on
load and refuses if they differ; the answer is to retrain, not to reinstall.

The technical detail is logged server-side; the caller gets a reason string and
never a stack trace.

## 8. Integration

**Health analysis** (`GET /api/dogs/<id>/medical/health-analysis`) gains one
key, `ml_anomalies`. Everything else is unchanged and byte-identical.

**The risk score is untouched.** ML anomalies contribute zero points. The score
means today exactly what it meant before this layer existed, so a model change
can never silently move it, and the rule-based breakdown stays complete. A test
asserts the score is identical with the model enabled and disabled.

**Alerts.** Only `high` anomalies become alerts, under the finding code
`ml.health_anomaly`, recorded at `moderate` severity — deliberately below the
deterministic highs, because a missed follow-up is a fact while an unusual
reading is a suggestion. Identity is the observation, so each flagged
observation is one alert, deduplicated and reopened by the normal Phase 5
lifecycle. The model version, score and reasons are kept as evidence.

**Dashboard.** A separate "AI / ML health anomaly detection" section, below the
rule-based findings, carrying the disclaimer, model version, score, severity in
words, affected observation and the reasons in plain English.

## 9. Limitations

1. **Trained on synthetic data.** The largest limitation. It has learned a
   simulation's notion of unusual, not a clinic's.
2. **Sustained shifts fade.** A rolling baseline adapts, so a persistent
   abnormality stops looking unusual (see §5). The rules cover this.
3. **Needs history.** Four observations minimum; most dogs in the system have
   fewer, so for them the layer honestly reports `insufficient_history`.
4. **Two measurements only.** Weight and temperature. Symptoms are free text
   and unmodelled.
5. **No calibration.** The score has no probabilistic meaning and must never be
   presented as a percentage chance.
6. **Not evaluated against clinical outcomes**, because no such labels exist
   here. Every number in §5 is measured against synthetic labels.
7. **Contamination sets the flag rate.** Roughly 6–7% of scored observations
   will be flagged by construction; on a large enough population some of those
   will be ordinary readings.

---

## 10. Privacy

No medical data leaves the server: the model runs in-process, and no external
AI service is called. The artifact holds no user data. All medical endpoints
require authentication, writes require admin, and public dog endpoints are
unchanged and carry nothing medical beyond the existing `medical_needs` flag.
