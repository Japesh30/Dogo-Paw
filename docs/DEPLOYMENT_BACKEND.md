## 2. The WSGI application object

`gunicorn app:app` means *"import the module `app.py`, serve the object named
`app` inside it"*. That object already exists at the bottom of `app.py`:

```python
app = create_app()
```

It is a real `Flask` instance and a valid WSGI callable — **verified**, not
assumed. No `wsgi.py` shim was added, because there is nothing for one to do
here; a second entry point would only be another thing to keep in step.

**Flask's development server is never used in production.** Three independent
guards, from Phase 3:

1. `app.config["DEBUG"] = False`, set unconditionally.
2. `app.run(...)` lives only under `if __name__ == "__main__"`, which gunicorn
   never executes.
3. That block refuses to run at all when `APP_ENV=production`, exiting with a
   message pointing at `gunicorn app:app`.

### Why `rootDir: app/backend` matters

The backend's modules are top-level imports (`from auth import ...`,
`from models import ...`), not a package. Gunicorn puts its working directory on
`sys.path`, so it must start **inside `app/backend`**. Setting `rootDir` is what
makes both `app:app` and those imports resolve. Running `gunicorn app:app` from
the repository root fails with `ModuleNotFoundError: No module named 'app'`.

## 3. Gunicorn configuration

Settings live in [`app/backend/gunicorn.conf.py`](../app/backend/gunicorn.conf.py),
which gunicorn picks up automatically from the working directory. That keeps the
start command short and the *reasoning* next to the numbers.

| Setting | Value | Why |
|---|---|---|
| `bind` | `0.0.0.0:$PORT` | Render injects `PORT`. Binding `0.0.0.0` rather than localhost is what makes the container reachable |
| `workers` | **2** (`WEB_CONCURRENCY`) | See below — this is the one that bites |
| `threads` | 4, `gthread` | Requests are mostly spent waiting on PostgreSQL; threads share the loaded libraries instead of duplicating them |
| `timeout` | 120 s | Boot is slow on a cold instance: importing scikit-learn, unpickling two models, seeding |
| `max_requests` | 1000 (+jitter) | Cheap insurance against a slow leak |
| `preload_app` | **False** | Deliberate — see below |
| `accesslog`/`errorlog` | `-` | Render captures stdout/stderr |

### The worker count is the trap

Measured on this application — Flask, SQLAlchemy, numpy, scipy, scikit-learn and
both trained models — **one worker is ~158 MB resident**. Render's free instance
has **512 MB**.

| Workers | Memory | Verdict |
|---|---|---|
| 1 | ~158 MB | fine |
| **2** | **~317 MB** | **chosen — real headroom** |
| 3 | ~475 MB | one spike from the ceiling |
| 4 | ~634 MB | OOM |

Gunicorn's default is `(2 × CPU) + 1`. A Render free instance reports the
**host** CPU count rather than its 0.1 CPU share, so the default works out at
**seventeen or more workers — roughly 2.7 GB** — and the instance is OOM-killed
before serving a single request.

> This is the most likely way this deployment would fail, and the symptom
> ("deploy succeeded, service won't start") does not point at the cause. Hence
> `workers` is pinned explicitly and `WEB_CONCURRENCY=2` is set in the blueprint.

### Why `preload_app` is off

Preloading would import once and fork, saving ~120 MB of duplicated libraries.
It would also fork *after* SQLAlchemy has opened connections, and a TCP socket
shared by two processes corrupts both sides. The correct fix is a `post_fork`
hook disposing the engine pool — one more moving part to get right. Two workers
already fit comfortably, so the memory is not needed. The note in
`gunicorn.conf.py` says exactly what to add if this ever moves to a bigger
instance.

### Logging does not leak tokens

`access_log_format` records method, path, status, size and duration. It does
**not** record headers, so no `Authorization` header or bearer token can reach
the logs.

## 4. Environment variables

| Variable | Required | Value | Set where |
|---|---|---|---|
| `APP_ENV` | **yes** | `production` | blueprint |
| `PYTHON_VERSION` | **yes** | `3.13.7` | blueprint |
| `SECRET_KEY` | **yes** | auto-generated by Render | blueprint (`generateValue`) |
| `WEB_CONCURRENCY` | recommended | `2` | blueprint |
| `DATABASE_URL` | **yes** | Supabase pooler URL | **dashboard** |
| `ADMIN_PASSWORD` | **yes** | your choice, min 12 chars | **dashboard** |
| `CORS_ORIGINS` | **yes** | your Vercel origin | **dashboard** |
| `PORT` | no | injected by Render | — |
| `RATE_LIMIT_ENABLED` | no | defaults on; leave alone | — |

### `APP_ENV=production` is the important one

It is the single flag that switches on every strict check. Without it the app
runs in development mode and every relaxed default applies — a generated signing
key, localhost CORS, and the demo adopter account seeded. **If you set only one
variable correctly, make it this one.**

With it set, the app **refuses to start** unless:

- `SECRET_KEY` is set and ≥ 32 characters
- `CORS_ORIGINS` is set and is not `*`
- `ADMIN_PASSWORD` is set and ≥ 12 characters

That is intentional. A misconfigured deployment that *runs* is far worse than
one that fails loudly at boot.

### Values you must supply

```
DATABASE_URL = postgresql://postgres.PROJECT_REF:PASSWORD@aws-0-REGION.pooler.supabase.com:6543/postgres?sslmode=require
CORS_ORIGINS = https://your-app.vercel.app
ADMIN_PASSWORD = <a strong password, 12+ characters>
```

Use the Supabase **session pooler on port 6543**, not the direct connection —
see [`DATABASE.md`](DATABASE.md) §3. Keep `?sslmode=require`.

> **No secret belongs in `render.yaml`.** It is committed. Every secret there is
> declared `sync: false`, which tells Render "this exists, ask the operator" —
> the value is entered in the dashboard and never stored in the repository.

## 5. Python version

Pinned to **3.13.7** in two places, which agree: `PYTHON_VERSION` in
`render.yaml` and `app/backend/.python-version`.

Pinning matters because a change to Render's default base image could otherwise
move the app to a Python with no prebuilt wheels for numpy, scipy or
scikit-learn — and a source build of scipy on a free instance will exhaust the
build timeout.

**Linux wheel availability was verified** for every compiled dependency:

| Package | cp313 | cp314 |
|---|---|---|
| `numpy==2.5.1` | ✅ | ✅ |
| `scipy==1.18.0` | ✅ | ✅ |
| `scikit-learn==1.9.0` | ✅ | ✅ |
| `psycopg-binary==3.3.6` | ✅ | ✅ |
| `joblib==1.5.3` | ✅ | ✅ |

### An honest caveat

**Local development and all testing ran on Python 3.14.3**, because that is what
is installed on this machine; 3.13 was not available to test against. The
deployment pins 3.13.7 because Render's support for it is certain, whereas 3.14
may not yet be offered.

The risk is low and worth stating precisely:

- Every dependency is pinned to an exact version, and those versions have cp313
  Linux wheels (verified above).
- The trained models are **pickle protocol 5**, readable by any Python 3.8+.
  Pickle compatibility depends on the *library* version, not the Python minor
  version, and `scikit-learn==1.9.0` / `joblib==1.5.3` / `numpy==2.5.1` are
  pinned identically.

It is not zero, though, so **run the verification in §8 after the first deploy**
rather than assuming. If Render does offer 3.14, changing both pins to `3.14.3`
makes the deployed runtime identical to the tested one, which is the stronger
position.

## 6. Deploying

### Option A — Blueprint (recommended)

[`render.yaml`](../render.yaml) already describes the service.

1. Push the repository to GitHub. *(Not done yet — Phase 7.)*
2. Render dashboard → **New → Blueprint**.
3. Select the repository. Render reads `render.yaml`.
4. It will prompt for the three `sync: false` variables — `DATABASE_URL`,
   `ADMIN_PASSWORD`, `CORS_ORIGINS`. Paste them.
5. **Apply**.

### Option B — Manual web service

**New → Web Service**, then:

| Field | Value |
|---|---|
| Runtime | Python 3 |
| Root Directory | `app/backend` |
| Build Command | `pip install -r requirements.txt` |
| Start Command | `gunicorn app:app` |
| Health Check Path | `/api/health` |
| Instance Type | Free |

Then add every variable from §4 under **Environment**.

### `CORS_ORIGINS` chicken-and-egg

The backend needs the Vercel URL, which does not exist until the frontend is
deployed. Deploy the backend first with a placeholder, then come back and set
the real origin once Vercel has given you a domain. Changing the variable
triggers a restart, which takes under a minute.

## 7. Database initialization

Nothing to run. `seed()` executes inside `create_app()` on first boot and is
idempotent — it creates missing tables, inserts the 18 dogs if the table is
empty, and creates the admin account if that email does not exist. No user data
is ever overwritten.

Concurrent workers are safe: seeding is wrapped in a **PostgreSQL advisory
lock**, so the first worker in does the work and the others wait, then no-op.
This is why no release command or migration step is needed. Full detail in
[`DATABASE.md`](DATABASE.md) §6.

In production the seed creates the admin account **only** — the demo adopter is
not created, and the admin password comes from `ADMIN_PASSWORD`.

## 8. Verifying the deployment

Replace `YOUR-APP` with the Render URL.

```bash
# 1. Liveness — the health check Render itself uses
curl https://YOUR-APP.onrender.com/api/health
# {"status":"ok","time":"..."}

# 2. Data and the database behind it
curl https://YOUR-APP.onrender.com/api/dogs | head -c 200
# {"count":18,...}

# 3. ML models loaded from disk
curl https://YOUR-APP.onrender.com/api/model-info
# metrics + coefficients, NOT 503

# 4. Admin login with your ADMIN_PASSWORD
curl -X POST https://YOUR-APP.onrender.com/api/auth/login \
  -H "Content-Type: application/json" \
  -d '{"email":"admin@dogo-paw.org","password":"YOUR_ADMIN_PASSWORD"}'
# a token

# 5. The dev password must NOT work
curl -X POST https://YOUR-APP.onrender.com/api/auth/login \
  -H "Content-Type: application/json" \
  -d '{"email":"admin@dogo-paw.org","password":"admin123"}'
# {"error":"Email or password is incorrect."}  <- 401 is the correct answer

# 6. Admin routes are guarded
curl -i https://YOUR-APP.onrender.com/api/admin/stats
# 401

# 7. CORS is pinned to your frontend
curl -i -H "Origin: https://evil.example.com" https://YOUR-APP.onrender.com/api/dogs | grep -i access-control
# no Access-Control-Allow-Origin header
```

Then run the database verification against production — 31 checks covering
schema, constraints, foreign keys, timestamps and column widths:

```bash
cd app/backend
DATABASE_URL="<your supabase url>" APP_ENV=production \
SECRET_KEY="<any 32+ chars>" ADMIN_PASSWORD="<your password>" \
CORS_ORIGINS="https://your-app.vercel.app" \
python verify_db.py
```

Checking the logs: Render dashboard → your service → **Logs**. On a healthy boot
you should see `database: postgresql (production)`, `loaded success predictor`,
`loaded intent classifier`, then gunicorn's `Booting worker` twice.

## 9. Free-tier behaviour to expect

| Behaviour | Detail |
|---|---|
| **Cold starts** | The instance sleeps after ~15 minutes idle and takes **~50 s** to wake. The first request after idling will be slow or time out |
| **Rate limits reset** | They live in memory, so a restart clears the counters |
| **Per-worker limits** | 2 workers means the effective rate limit is up to 2× the configured one. See [`SECURITY.md`](SECURITY.md) §5 |
| **Ephemeral disk** | Nothing written to disk survives a restart. This is exactly why `SECRET_KEY` must be an environment variable |

**Before a viva or demo, open the site a minute beforehand** to wake the
instance. A cold start mid-demo looks like a broken deployment, and the frontend
will show its "could not reach the server" message.

## 11. Troubleshooting

| Symptom | Cause | Fix |
|---|---|---|
| Build succeeds, service never starts, no clear error | Too many workers → OOM | Set `WEB_CONCURRENCY=2` |
| `ModuleNotFoundError: No module named 'app'` | Root directory not set | Set Root Directory to `app/backend` |
| `SECRET_KEY must be set when APP_ENV=production` | Missing variable | Add it (or let the blueprint generate it) |
| `CORS_ORIGINS='*' is not allowed` | Wildcard in production | Set the exact Vercel origin |
| `ADMIN_PASSWORD must be set` | Missing variable | Add one, 12+ characters |
| `Can't load plugin: sqlalchemy.dialects:postgres` | `DATABASE_URL` bypassed normalisation | Use the app's own config path; see [`DATABASE.md`](DATABASE.md) §3 |
| `too many connections` | Direct Supabase connection (5432) | Use the pooler (6543) |
| Worker timeout during boot | Model loading slower than the timeout | `timeout = 120` is already set; confirm the config file is being read |
| Frontend says "could not reach the server" | Cold start, or `CORS_ORIGINS` wrong | Wait ~50 s and retry; check the origin matches exactly, including `https://` and no trailing slash |
| `/api/model-info` returns 503 | Artifacts missing from the deploy | Confirm `ml/artifacts/*.joblib` are committed |
